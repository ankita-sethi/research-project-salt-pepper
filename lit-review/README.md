# Literature Review
## Static analysis
[1] performed a developer survey of Automatic Static Analysis Tools (ASAT) usage. The findings show developers use ASAT results during development, code reviews, and Continuous Integrations (CI). However, they do not enable different warnings in different development contexts, which hints at the possibility of ignoring the warnings based on the context. In [2], it was found that only a minority (8.76%) of the issues reported were fixed, and 80% of the fixes targeted 20% of the ASAT rules. Our work targets to find if the ignored ASAT issues could lead to potential vulnerabilities in the codebase. [5] analyzed 20 Java open-source projects to identify the pattern of static analysis usage and how developers responded to the warnings and errors reported by ASATs. Even though the majority of the reports were fixed, there were small portions which were ignored by changing configurations. Even though this work does not target security analyzers, we try to uncover if a similar configuration change is being done in the usage of security analyzers. [3] performed mining of ASAT reported violations and the fixes and concluded that only a small fraction of violations were actually fixed by the developers, and this is due to the large false positive ratio in the ASATs or lack of developer interest in fixing lower severity bugs. This work also implemented automatic fix generation for the issues reported by analyzers. Our work will perform a deep-dive on the types of issues that are ignored by the developers and also target to find and report such instances automatically. This also will give an estimate of what percentage of ignored issues were actually false positives.[9] This study classifies strategies for applying static code analysis tools, providing a structured framework for their implementation. The identified strategies encompass two main categories: running a tool over a completed software project and employing a static analysis tool during software project development. It introduces strategies for effectively using static code analysis tools. It categorizes these strategies into two main classes: running the tool over a completed software project (S1) and integrating it into the development process (S2). Each sub-strategy is mapped to the standard code review cycle, outlining the steps involved in its implementation. These strategies aim to optimize code quality by leveraging static code analysis tools effectively throughout the development process.

In addition, the previous paper discussed above [13] talks about how ASATs require configuration tailored to the specific context of a project, and unfortunately, they are often barely configured according to their use case, also many developers tend to leave them unchanged and rely on default settings provided by the ASAT. Consequently, a significant number of ASAT warnings go unaddressed, raising the question of whether these warnings may lead to vulnerabilities. This makes us think about what about those cases where ASAT's were made to consider exceptions in the code. Are they safe?

## Python ecosystem
[4] analyzed how a vulnerability in one Python package can impact a large number of dependent packages, thus leading to the possibility of exploiting any codebase dependent on these. Each of the top 10,000 packages in the PyPi was imported by an average of 250 packages (termed Package Reach), thus hinting at how important it is that not only for the codebase to be secure but also for all the dependent codebases to be secure. [10] investigates the concept of technical leverage in the Python ecosystem. Technical leverage is the ratio between dependencies (other people's code) and own code in a software package. The study found that small Python package versions have a median technical leverage of 6.9x their own code, while bigger package versions rely on dependencies code a tenth of their own (median leverage of 0.1). This shows how highly dependent one Python package can be on others. This basically elevates the impact of the vulnerability in one Python package to many other applications.

Proposal [6] is for Python's Bandit to add an option to force the developers to include an explanation of each of the `#nosec` exceptions. This also suggests that there is a lack of understanding of why the exceptions were added originally to the repository.

## Vulnerabilities in Python Packages
[11]talks about the widespread vulnerabilities in Python packages. And the number of discovered vulnerabilities in Python packages is increasing over time. It also talks about various distributions of vulnerabilities. The most common types of vulnerabilities are input validation (32.55%), cross-site scripting (18.73%), and remote code execution (13.27%). [12] Reports the most common vulnerabilities in Python packages and ranks them according to CWE, the most common vulnerability categories reported are "Improper neutralization of special elements in OS commands (command injections)", "Hardcoded password" and "Insufficient quality of random values" according to CWE Categories. From this, we can understand that there is a need for frequent detection of vulnerabilities in Python open-source projects. Our work is focused on just taking one step ahead to identify vulnerabilities in Python repositories that have been assumed to be safe. [12] uses Bandit for detecting vulnerabilities in Python packages because of its wide range of testing modules and the flexibility to build custom plugins. However, the paper doesn't delve into analysing part of the code which has been marked for exceptions using `#nosec`", which our work focuses on doing.


## Static Analysis for web applications and Java projects
[7] This article meticulously assesses the efficacy of open-source tools designed for executing static code analysis for security purposes. The research encompassed a broad spectrum of programming languages, including Java, JavaScript, PHP, and Python, and involved the analysis of sixteen vulnerable web applications and each detected vulnerability was categorized into one of three labels: True
Positives (TP), False Positives (FP), or Not Applicable (N/A). It is imperative to emphasize that the deliberate inclusion of security
vulnerabilities in the test applications amplifies the real-world relevance of this study’s outcomes. [8] This study presents a comprehensive evaluation of six prominent static analysis tools (Better Code Hub, CheckStyle, Coverity Scan, FindBugs, PMD, and SonarQube) in terms of their effectiveness in detecting static analysis rules. The assessment encompassed 47 Java projects sourced from the Qualitas Corpus dataset, where they identified and compared rules detectable by each tool. The results reveal minimal agreement among the tools and a low degree of precision.
