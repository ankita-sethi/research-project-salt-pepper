# Literature Review
## Static analysis
[1] performed a developer survey of Automatic Static Analysis Tools (ASAT) usage. The findings show developers use ASAT results during development, code reviews, and Continuous Integrations (CI). However, they do not enable different warnings in different development contexts, which hints at the possibility of ignoring the warnings based on the context. In [2], it was found that only a minority (8.76%) of the issues reported were fixed, and 80% of the fixes targeted 20% of the ASAT rules. Our work targets to find if the ignored ASAT issues could lead to potential vulnerabilities in the codebase. [5] analyzed 20 Java open-source projects to identify the pattern of static analysis usage and how developers responded to the warnings and errors reported by ASATs. Even though the majority of the reports were fixed, there were small portions which were ignored by changing configurations. Even though this work does not target security analyzers, we try to uncover if a similar configuration change is being done in the usage of security analyzers. [3] performed mining of ASAT reported violations and the fixes and concluded that only a small fraction of violations were actually fixed by the developers, and this is due to the large false positive ratio in the ASATs or lack of developer interest in fixing lower severity bugs. This work also implemented automatic fix generation for the issues reported by analyzers. Our work will perform a deep-dive on the types of issues that are ignored by the developers and also target to find and report such instances automatically. This also will give an estimate of what percentage of ignored issues were actually false positives.

## Python ecosystem
[4] analyzed how a vulnerability in one Python package can impact a large number of dependent packages, thus leading to the possibility of exploiting any codebase dependent on these. Each of the top 10,000 packages in the PyPi was imported by an average of 250 packages (termed Package Reach), thus hinting at how important it is that not only for the codebase to be secure but also for all the dependent codebases to be secure. Proposal [6] is for Python's Bandit to add an option to force the developers to include an explanation of each of the `#nosec` exceptions. This also suggests that there is a lack of understanding of why the exceptions were added originally to the repository.
